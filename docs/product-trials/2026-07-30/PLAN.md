# Ten-product validation plan

## Purpose

Use the packaged application as a user to design, build, connect, and verify ten realistic products. Start each product with a small repository that contains only a brief, test runner, and package manifest. Apply implementation files only through the Build workflow.

## Products

1. DO-178C Review Workbench
2. Copilot Session Operations Hub
3. Technical Writing and Review Desk
4. Flight-Test Telemetry Triage Console
5. Aircraft Performance Trade-Study Workbench
6. HIL Test Campaign Orchestrator
7. Supplier Deliverable Intake Portal
8. Requirements Change-Impact Workbench
9. Avionics Software Load and Configuration Manager
10. Reliability and FRACAS Investigation System

## Acceptance criteria for each product

- Create a new project in the packaged application.
- Complete the project setup.
- create and approve the use-case analysis from five positive examples and one prohibited result.
- Review the generated application workflow.
- Create and approve an experience-first system structure.
- Complete and approve the Application workflow and User workspace module designs.
- Inspect the component, activity, state-machine, sequence, and use-case diagrams.
- Create and approve the design baseline.
- Create the implementation handoff.
- Inspect and apply the product implementation through Build.
- Open the built UI at desktop and mobile sizes.
- Exercise positive and protected product actions.
- Map every approved scenario to a real UI action and visible result.
- Verify all six scenarios.
- Approve the exact verification result.
- Inspect immutable evidence and the original screenshot.
- Record interaction counts, phase durations, renderer errors, product errors, warnings, screenshots, and findings.

## Scorecard

Use a zero-to-ten scale. Do not award ten without direct evidence.

### Commercial potential

- Problem value: The product solves an expensive or frequent problem.
- Differentiation: The workflow creates value that generic AI or diagram tools do not create.
- Product proof: The approved intent traces to a working interface and evidence.
- Pilot readiness: A design partner can complete a useful trial without hidden work.
- Self-service readiness: A new user can succeed without a bespoke acceptance script.
- Enterprise readiness: The product supports controlled review, identity, policy, deployment, and administration.
- Long-term monetization: The product can become part of a durable engineering process.
- Scalable revenue: Delivery and support effort do not grow in direct proportion to customers.

### Product quality

- Usability: The next action, current state, and recovery path are clear.
- Efficiency: The workflow avoids repeated input and low-value waiting.
- Presentation: The UI and design outputs look credible in a customer review.
- Confidence: The product explains what is proved, what is inferred, and what remains.
- Delight: Progress has useful feedback, visible momentum, and satisfying completion.

## Evaluation rule

Convert repeated friction into a reusable product change. Do not hide a product defect in the trial automation. Re-run representative journeys after each shared fix.
